# CEQWA Website

Static GitHub Pages website for the Central Excise Quarters Residents' Welfare
Association (CEQWA), CSEZ, Kakkanad, Cochin.

## Structure

- `index.html` — home page
- `about.html` — about the organization
- `documents.html` — official documents
- `financials.html` — financial statements
- `contact.html` — contact information
- `css/style.css` — design system (CSS custom properties)
- `js/main.js` — theme toggle, mobile navigation, footer year
- `js/chart-colors.js` — deterministic, theme-aware chart palette and chart layout helpers
- `js/tables.js` — renders tables from JSON
- `data/finances/finances.json` — canonical transaction-level financial source of truth
- `data/metadata.json` — canonical document and published statement metadata
- `data/financials-dashboard.json` — validated dashboard series and presentation breakdowns
- `scripts/` — maintenance, fixture, and validation scripts
- `.github/workflows/validate.yml` — CI checks run on pushes and pull requests
- `skills/` — portable AI maintenance instructions
- `documents/` — upload official documents here
- `financials/` — upload financial statements here (PDF plus machine-readable Markdown companion, e.g. `05.2026.pdf` / `05.2026.md`)

The older `data/documents.json` and `data/financials.json` files are retained
only for data preservation. They are legacy files, are not read by the website,
MCP tools, or validators, and may be removed in a future cleanup. Use
`data/metadata.json` for all future metadata changes.

## Design system

Most visual tokens live as CSS custom properties in `:root` and
`[data-theme="dark"]`:

- Colors (`--bg`, `--surface`, `--text`, `--border`, `--primary`, `--accent`, nav colors)
- Spacing (`--space-1` … `--space-8`)
- Radii (`--radius-sm/md/lg`)
- Shadows (`--shadow-sm/md`)
- Type scale (`--fs-xs` … `--fs-3xl`)
- Transitions (`--transition`)

Chart colors are generated by `js/chart-colors.js` from evenly spaced hues,
with brightness adjusted for the active theme. Chart segments also use the
current surface color as a separator so adjacent categories remain distinct.

Dark mode is toggled via `data-theme` on `<html>`, persisted in `localStorage`,
and defaults to the user's `prefers-color-scheme`.

## Data ownership and financial periods

`data/finances/finances.json` is the only authoritative transaction dataset.
Each transaction has a stable `transaction_id`, a `date` or explicit `null`,
source wording, flow tags, recurrence, and an `accounting_class` of
`income`, `opex`, `capex`, or `opening_balance`.

Do not edit financial amounts to satisfy a test. Preserve the original PDF and
source wording. Opening balances are not income and must use
`recurrence: "not_applicable"`.

`data/metadata.json` contains the `financials` metadata array. A statement period must
include `period_id`, `period_label`, `source_label`, `period_type`,
`start_date`, and `end_date`. Period labels must describe the actual source
coverage; for example, the first published period is
`22 Dec 2025–18 May 2026`, not simply May 2026. The optional
`allowed_out_of_period_dates` field documents an explicitly evidenced date
outside the main coverage window.

Metadata is strict: both top-level arrays are required, document `file` paths and
financial `period_id`, `period`, and source `file` values must be unique, and
published file paths must exist. Unknown metadata fields are rejected. Financial
periods are ordered chronologically by `start_date` (then end date, ID, and file).

The published statement amount includes opening balances. Dashboard income
excludes opening balances. Closing balances must satisfy:

```text
opening balance + income - expenses = closing balance
```

CAPEX is reported separately from OPEX. One-off and special-purpose income
must not be described as recurring income.

## Adding a document

Documents and financials are rendered from `data/metadata.json`. Financial period labels are
not assumed to be calendar months: each published statement carries explicit
start/end dates and a period type.

1. Drop the file into `documents/` (or `financials/`)
2. Add an entry to the `documents` (or `financials`) array in `data/metadata.json`
3. Commit and push to `main` — GitHub Pages updates automatically

### `metadata.json` format

The `#` column is auto-generated.

```json
{
  "documents": [
    {
      "title": "Constitution & Bye-laws",
      "category": "Governance",
      "date": "2025",
      "file": "documents/constitution.pdf"
    }
  ],
  "financials": []
}
```

Financial statement entries use the `financials` array:

```json
{
  "description": "Sources and Uses of Funds Statement - June 2026",
  "period": "June 2026",
  "period_id": "2026-06",
  "period_label": "June 2026",
  "source_label": "June 2026",
  "period_type": "calendar_month",
  "start_date": "2026-06-01",
  "end_date": "2026-06-30",
  "amount": "Rs. 51,422",
  "file": "financials/06.2026.pdf",
  "markdown": "financials/06.2026.md"
}
```

Each financial statement is published as both a PDF (human-readable) and a
Markdown file (machine-readable, with YAML front matter and plain-number
tables). The Finances tab shows a `Markdown` link next to `Download` when the
`markdown` field is present.

For MCP document uploads, place the source file in ignored `incoming/` and use
`ceqwa_propose_document_add`. The proposal is reviewed, approved, and executed
before the file is copied into `documents/` and its metadata is appended to the
`documents` array. If no Markdown companion is supplied, no `markdown` field is
written. Financial uploads use `ceqwa_propose_financial_import` instead; that
workflow copies the PDF into `financials/`, generates the Markdown companion,
updates the `financials` array, canonical transactions, and dashboard data, and
requires reconciliation to pass.

### Validate the site

Run these zero-dependency checks from the repository root before publishing:

```bash
python scripts/validate_finances.py
python scripts/test_financial_fixtures.py
python scripts/validate_site.py
Get-ChildItem js/*.js | ForEach-Object { node --check $_.FullName }
```

## CEQWA MCP Administration

`ops/` is a local, administrative MCP server for Nanobot. It does not run on
GitHub Pages and does not change the static-site architecture. Nanobot reads
PDFs and interprets user intent; CEQWA MCP validates structured proposals and
performs only approved semantic operations.

Install the server in a virtual environment with:

```bash
python -m pip install -e .
```

Start the stdio server with:

```bash
python -m ops.mcp_server
```

A minimal Nanobot MCP configuration for this checkout is:

```json
{
  "mcp_servers": {
    "ceqwa": {
      "command": "python",
      "args": ["-m", "ops.mcp_server"],
      "cwd": "<absolute-path-to-this-repository>"
    }
  }
}
```

Use a repository-specific absolute `cwd` on the host running Nanobot. The
server exposes read-only status, validation, financial queries, document
helpers, and Git inspection freely. Every mutation is a three-phase operation:
`propose`, `ceqwa_approve_proposal`, then `ceqwa_execute_proposal`. Approval is
bound to a SHA-256 hash of the canonical payload, expires after 30 minutes by
default, and is single-use. Nanobot interprets conversational consent; MCP
does not pretend to authenticate the human.

Financial imports preserve the original PDF, add a deterministic Markdown
companion, update the single canonical `data/finances/finances.json`, rebuild
the dashboard, detect duplicates, enforce reconciliation and continuity, and
roll back the complete batch if validation fails. Commit and publish are
separate approval-gated operations. Runtime proposals, locks, and audit logs
are stored in ignored `.ceqwa-mcp/`; incoming files may be placed in ignored
`incoming/`.

Run the administration tests with:

```bash
python -m unittest discover -s ops/tests -v
```

The optional `pdf` extra adds PDF parsing/rendering support. OCR is optional and
is explicitly evidence for Nanobot, never authoritative financial data:

```bash
python -m pip install -e ".[pdf]"
```

The transport descriptions document the available tools and their approval
requirements. There is intentionally no generic shell, Python, arbitrary file
write, or arbitrary file delete tool.

The financial validator checks JSON structure, statement links, Markdown
companions, stable transaction IDs, ISO dates, tags, recurrence, CAPEX/OPEX
classification, dashboard alignment, continuity, and reconciliation. The
fixture test confirms malformed financial data is rejected. The site validator
checks JSON syntax, duplicate HTML IDs, and local asset/document references.
The GitHub Actions workflow runs these checks automatically on pushes and pull
requests.

## Local preview

```
python -m http.server 8000
```

Then visit `http://localhost:8000`. Check all financial tabs, every period
selector, document links, light/dark themes, and a narrow viewport. Financial
tables and statement links remain available if JavaScript or Plotly is
unavailable.
